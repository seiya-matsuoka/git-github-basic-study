# 00-02 用語集

## 1. この項目で学ぶこと

この項目では、Git / GitHub の学習で何度も登場する基本用語を整理する。

---

## 2. 事前に理解しておきたいこと

Git は単に「コミットして push するツール」ではない。  
ファイルの状態、履歴、分岐、統合、復旧などを管理する仕組みであり、その理解には用語の整理がとても重要である。

今後の学習では、次のような言葉が何度も出てくる。

- working tree
- staging area
- HEAD
- branch
- merge
- origin
- tracking branch

これらを曖昧なまま進めると、`status` や `log` の表示を正しく読みにくくなる。  
分からなくなったら、この用語集に戻って確認する。

---

## 3. 用語一覧

### Git

バージョン管理システム。
ファイルの変更履歴を記録し、過去との差分確認、履歴の追跡、ブランチによる分岐、マージによる統合、取り消しや復旧などを行える。

### GitHub

Git のリポジトリをホストし、共有やレビュー、Pull Request、履歴の可視化などを行うためのサービス。
Git そのものではなく、Git を使った共同作業や公開、運用を助ける場所と考えると分かりやすい。

### repository

変更履歴を管理する単位。
一般に「リポジトリ」と呼ぶ。
Git では、履歴や設定を含んだ管理単位を指す。

### local repository

自分の PC 上にある Git のリポジトリ。
コミットやブランチ作成など、多くの操作はまずローカルで行う。

### remote repository

GitHub などの外部サービス上にあるリポジトリ。
共有やバックアップ、Pull Request などに使う。

### working tree

今まさに自分が編集している作業中のファイルの状態。
エディタで開いて変更しているファイル群がある場所、と考えると分かりやすい。

### staging area

コミットに含める変更を一時的に載せる場所。
`git add` で変更をここに乗せる。
working tree と commit の間にある中間地点。

### index

staging area とほぼ同じ意味で使われる。
Git の内部的な表現として index という言葉が出ることがある。

### tracked file

Git が追跡対象として認識しているファイル。
一度 add や commit の対象になったファイルは tracked として扱われる。

### untracked file

Git がまだ追跡していないファイル。
新しく作っただけで add していないファイルなどがこれに当たる。

### commit

その時点の変更内容を履歴として記録したもの。
単なる「保存」ではなく、「この変更をこの単位で履歴に残す」という意味を持つ。

### commit message

コミットに付ける説明文。
「何を変更したのか」が分かるように書く。

### history

コミットの積み重ねによって作られる変更履歴全体。
`git log` で確認する。

### diff

ある状態とある状態の差分。
変更前後で何が変わったかを見るための情報。

### branch

履歴の流れを分岐させるための仕組み。
作業の流れを分けて安全に変更を進めるために使う。
実務では、main に直接作業せず、feature branch を切って作業することが多い。

### main

通常、中心となる基準ブランチ。
以前は `master` が使われることも多かったが、現在は `main` を使うことが多い。

### feature branch

機能追加や修正のために main から分岐して作る作業用ブランチ。
実務では、1つの作業ごとにブランチを切ることが多い。

### HEAD

現在自分がどのブランチ・どのコミットを見ているかを示す位置情報。
「今の自分の現在地」と考えると分かりやすい。

### switch

現在いるブランチを切り替える操作。
`git switch` を使う。

### checkout

以前から使われている多機能なコマンド。
ブランチ切り替えやファイル復元など複数の役割がある。
最近は役割を分けて `switch` や `restore` を使う場面が増えている。

### merge

分岐したブランチの変更を統合すること。
feature branch の変更を main に取り込む、という場面で使う。

### fast-forward merge

履歴が一直線につながる場合に、単にポインタが前に進む形で統合される merge。
追加の merge commit が作られないことがある。

### merge commit

マージの結果として作られる統合用のコミット。
分岐していた履歴を統合したことが履歴上で分かりやすくなる。

### conflict

別々の変更同士が衝突し、自動で統合できない状態。
同じファイルの同じ箇所を別ブランチで変更したときなどに起こる。

### conflict marker

コンフリクト時にファイル内へ挿入される印。
どちらの変更が衝突しているかを示す。
自分で解消してから add / commit する必要がある。

### restore

作業ツリーやステージの内容を戻すための操作。
編集中の変更を取り消したり、ステージを外したりするときに使う。

### amend

直前のコミットを修正すること。
コミットメッセージの修正や、コミットに入れ忘れた変更の追加などに使う。

### reset

ブランチの位置やステージ状態などを戻す操作。
`soft` / `mixed` / `hard` によって戻り方が変わる。
強力だが、理解せずに使うと混乱しやすい。

### revert

過去コミットの内容を打ち消す新しいコミットを作る操作。
履歴を残したまま変更を取り消したいときに使う。

### reflog

HEAD やブランチ参照の移動履歴。
reset や誤操作のあとに「どこにいたか」を探すのに役立つ。
復旧の最後の助けになることが多い。

### stash

作業途中の変更を一時退避する仕組み。
今の作業をコミットしたくないが、いったん片付けたいときに使う。

### tag

特定のコミットに付ける目印。
バージョン番号やリリースポイントを示すのによく使う。

### cherry-pick

ある特定のコミットだけを別のブランチへ取り込む操作。
便利だが、使いすぎると履歴が分かりにくくなることがある。

### origin

通常、自分が最初に登録したリモートリポジトリの名前。
多くの場合 GitHub 上の自分のリポジトリを指す。

### upstream

文脈によって意味が少し異なるが、一般には「追跡元」や「基準となるリモート・ブランチ」を指す。
fork 運用では元リポジトリを upstream、自分の fork を origin と呼ぶこともある。

### remote

ローカルの外にある Git リポジトリへの参照設定。
GitHub 上のリポジトリと紐づけるときに設定する。

### push

ローカルのコミットをリモートへ送る操作。
自分の PC の変更履歴を GitHub に反映させるイメージ。

### fetch

リモートの最新情報を取得する操作。
ただし、自分の作業ブランチへ自動統合はしない。
まず情報だけ取りに行くイメージ。

### pull

一般に、fetch してから現在のブランチへ反映する操作。
便利だが、何が起きるかを意識せずに使うと混乱しやすい。

### tracking branch

ローカルブランチが、どのリモートブランチを追跡しているかという関係。
これが設定されていると、push や pull が扱いやすくなる。

### origin/main

origin というリモート上の main ブランチを指す表現。
ローカルの main とは別物であることが重要。

### Pull Request

GitHub 上で「このブランチの変更を取り込んでほしい」と提案する仕組み。
レビュー、説明、履歴の確認、統合の判断などを行う場になる。

### GitHub Flow

シンプルなブランチ運用の流れ。
一般的には次のような流れを取る。

- main からブランチを切る
- 変更を加える
- push する
- Pull Request を作る
- 必要なら追加修正する
- merge する
- ブランチを削除する

### rebase

あるブランチの変更を、別の基準の上に積み直す操作。
履歴を直線的に見せやすくなるが、履歴の書き換えを伴うため注意が必要。

### squash

複数コミットを 1 つにまとめること。
PR マージ時や履歴整理で使われる。

### detached HEAD

HEAD がブランチではなく、特定のコミットそのものを直接指している状態。
この状態で作業すると、どのブランチにも属さないコミットを作って混乱しやすい。

## 4. よくあるミス・混乱ポイント

### Git と GitHub を同じものだと思う

Git はバージョン管理の仕組みであり、GitHub はそれを共有・運用するサービスである。

### working tree と staging area の区別が曖昧

この違いは今後の学習で最重要の 1 つ。
編集しただけでは commit されず、いったん staging area に載せる必要がある。

### branch を「フォルダの分岐」のように考えてしまう

branch は履歴の流れを分ける仕組みであり、ディレクトリのコピーではない。

### pull を何となく使う

pull は便利だが、裏で何が起きるかを知らずに使うと混乱しやすい。
今後の学習で fetch と比較しながら理解する。

### rebase を怖い操作としてだけ覚える

注意は必要だが、概念を理解すれば役割は整理しやすい。
今の段階では「履歴を積み直す考え方」と知っておけば十分。
